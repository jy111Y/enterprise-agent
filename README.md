为什么流式响应能改善用户体验；

它主要改善的是“首字等待时间”，即 Time to First Token，简称 TTFT。
即使答案仍需 10 秒才能生成完，用户可能在第 1 秒就看到文字，因此会感觉：
- 系统响应更快；
- 可以立即确认请求已经被处理；
- 长答案不再需要一直面对空白页面；
- 发现回答方向错误时，可以提前停止生成；
- 更接近真人逐步输入文字的交互体验。



为什么它通常不会降低完整生成耗时；

流式响应只是改变了答案的传输和展示方式，并没有让模型生成得更快。
完整耗时通常包含：
网络请求时间
+ 排队时间
+ 模型首字生成时间
+ 后续 Token 生成时间
+ 网络传输时间
流式响应降低的是用户感知延迟，不一定降低端到端完整耗时。由于需要处理多个数据块和事件，流式模式甚至可能产生少量额外传输与处理开销。



网络中断时如何处理；

流式中断的两种恢复策略
简单项目可以使用：
连接中断 → 放弃当前不完整回答 → 用户重新生成
生产项目可以使用：
连接中断
→ 根据请求ID查询任务状态
→ 如果任务已完成，获取完整结果
→ 如果任务失败，再决定是否重试
不要直接把“已收到的半段答案”和“重新生成的新答案”拼接，因为模型第二次生成的内容可能不同。



为什么生产项目要设置超时和重试。

超时的作用
如果没有超时，一次异常请求可能无限等待，占用：
- Web 服务器连接；
- 工作线程；
- 内存；
- 数据库连接；
- 用户并发额度。
最终一个模型服务故障可能拖垮整个应用。
超时不是越短越好。太短会错误终止本来可以成功的复杂推理请求，需要结合实际 P95/P99 延迟设置。

重试的作用
网络和模型服务可能发生短暂故障，例如：
- 临时连接失败；
- 请求超时；
- HTTP 429 限流；
- HTTP 500、502、503 等服务端错误。
这些问题稍后再次请求可能成功，因此需要有限次数的重试。
不是所有错误都应该重试


总结：流式响应解决“用户等得难受”，超时解决“请求一直不结束”，重试解决“暂时性故障”，幂等性解决“重试导致重复执行”。
